# ADMA Dashboard — Project Specification

Этот файл — постоянный источник требований для разработки ADMA Dashboard. Перед каждым новым этапом следует учитывать его вместе с текущим состоянием проекта. Не нужно повторно проводить полный аудит проекта на каждом этапе, если архитектура существенно не изменилась.

## 1. Цель

Развивать существующий ADMA Finance в единый ADMA Dashboard для управления ремонтными объектами компании. Не переписывать приложение с нуля и не дублировать уже существующие сущности или данные.

Центральная сущность системы — **Объект**.

Целевая логика связей:
- Дизайнер → Заявка → Объект
- Объект → График / Финансы / Команда / Документы / Задачи / Фото
- Мастер → Объект / Этап
- Общие расходы → ADMA

Одна сущность хранится один раз; разные экраны используют связи и агрегаты, а не копии данных.

## 2. Основная навигация

Целевое главное меню:
- Главная
- Объекты
- Финансы
- Заявки
- Дизайнеры
- Мастера

Отдельный глобальный раздел «График» не нужен. График относится к конкретному объекту. Общая информация по графикам при необходимости агрегируется на Главной.

## 3. Объекты

Объект — центральная сущность ADMA.

Внутри объекта:
**Обзор | График | Финансы | Команда | Документы | Задачи | Фото**

Основные данные: название/ЖК, адрес, площадь, заказчик и телефон, прораб, дизайнер, статус, процент готовности, даты начала/плановой и фактической сдачи, номер договора, гарантийный период, примечания.

Статусы: Подготовка, В работе, Приостановлен, Сдача, Гарантия, Архив.

## 4. Обзор объекта

Должен быстро показывать: общий прогресс, текущий/следующий этап, плановую сдачу, отклонение от графика, краткие финансы, ответственных и блок «Требует внимания». Не использовать фиктивные production-данные.

## 5. График объекта

Расположение: **Объекты → [Объект] → График**. Каждый этап связан с `object_id`.

Целевые поля: название, плановое/фактическое начало и окончание, процент выполнения, статус, ответственный, мастер/команда, стоимость работ, комментарий.

Статусы: Запланирован, В работе, Выполнен, Задерживается, Приостановлен. В дальнейшем рассчитывать отклонение от графика. Сложный Gantt не приоритет первой версии.

## 6. Финансы объекта

Расположение: **Объекты → [Объект] → Финансы**.

Обязательная структура: **Сводка | Акты | Накладные | Чеки / Разное**. Не объединять их в один список.

### Акты
Целевые данные: номер, дата, название/описание, этап, сумма, связанные оплаты/расходы, прибыль, статус, файл, комментарий.

**Сумма акта − связанные оплаты/расходы = прибыль по акту.**

### Накладные
Целевые данные: номер, дата, поставщик, описание, сумма, связанные оплаты, остаток, прибыль, статус, файл, комментарий.

**Сумма накладной − связанные оплаты = прибыль по накладной.**

### Чеки / Разное
Отдельный раздел для покупок/расходов, суммы которых необходимо получить обратно от заказчика.

**Критическое бизнес-правило: Чеки / Разное НЕ уменьшают прибыль объекта.** Они учитываются отдельно как суммы к возмещению/получению от заказчика.

Сохранять существующий рабочий PDF-экспорт и связанную логику.

## 7. Глобальные Финансы

Главное меню → **Финансы**. Это агрегированная картина ADMA, а не копия финансов объектов.

Структура: **Сводка | Общие расходы**.

Сводка в дальнейшем агрегирует прибыль объектов, суммы к получению, состояние активных объектов, общие расходы и итоговую прибыль ADMA.

### Общие расходы
Расходы компании вне конкретных объектов; `object_id` не требуется. Категории: реклама, сервисы/подписки, офис, транспорт, административные расходы, зарплаты, налоги, банковские расходы, прочее.

Поля: дата, сумма, категория, описание, комментарий, автор, файл/чек при необходимости.

**Прибыль всех объектов − Общие расходы = Итоговая прибыль ADMA.**

## 8. Команда и мастера

Внутри объекта «Команда» показывает ответственных и мастеров, назначенных на объект/этапы. Не создавать копии мастеров внутри объекта — использовать глобальную базу.

Карточка мастера: имя, телефон, Telegram, специализация, дополнительные навыки, внутренний рейтинг, уровень цен, заметки, история объектов, текущая занятость.

Занятость: Свободен / Освободится [дата] / Занят.

## 9. Дизайнеры

Глобальный раздел **Дизайнеры** — CRM. Воронка: **Найден → Первый контакт → Ответил → Встреча → Партнёр → Передал заявку → Есть объект → Неактивен**.

Карточка в дальнейшем содержит контакты, ответственного, последний/следующий контакт, заметки, историю, заявки, объекты и эффективность. Связь: **Дизайнер → Заявка → Объект**.

## 10. Заявки

Воронка: **Новая → Связались → Замер → Смета → Переговоры → Договор → Проиграна**.

Данные: клиент, телефон/Telegram, объект/ЖК, площадь, бюджет, наличие дизайн-проекта, желаемый старт, источник, ответственный, комментарии, история контактов.

Источники: Дизайнер, Рекомендация, Сайт, Instagram, Telegram, Flatica, Другое. Если источник — дизайнер, связывать с конкретным дизайнером CRM. Успешная заявка превращается в Объект без повторного ввода.

## 11. Документы объекта

Категории: Договор, Смета, Дополнительные соглашения, Дизайн-проект, Техническая документация, Прочее. Акты и Накладные здесь не дублировать — они принадлежат Финансам.

## 12. Задачи объекта

Простой операционный менеджер, не Trello-клон. Поля: название, описание, ответственный, дедлайн, приоритет, статус. Возможны связи с объектом, этапом, актом или накладной.

## 13. Фото объекта

Каждый объект имеет собственный раздел **Фото**. Фото разных объектов не смешиваются. Обязательная связь: **Фото → object_id**. В дальнейшем: **Фото → stage_id** и группировка по этапам. Глобальная фотогалерея в первой версии не нужна.

## 14. Главная

В конечном состоянии — агрегированный dashboard компании: активные объекты и прогресс, финансы, новые заявки, задачи, задержки, блок «Требует внимания». Использовать реальные данные по мере появления модулей.

## 15. Дизайн — обязательный визуальный эталон

Утверждённый GPT Sites макет ADMA Dashboard:
https://adma-finance-concept.ilyamaksimov86.chatgpt.site/

**Этот макет является обязательным визуальным референсом для всего приложения, а не только Главной страницы.** Перед созданием или существенным изменением UI сначала сверяться с ним.

Новые экраны должны использовать его визуальный язык: композицию, sidebar/навигацию, фон, карточки, типографическую иерархию, цветовую палитру, отступы, скругления, кнопки, таблицы/списки, фильтры/формы, бейджи/статусы и визуальную плотность.

Если конкретного экрана нет в макете, использовать существующие паттерны макета вместо создания отдельного стиля.

Приоритет разработки: **архитектура → функциональность → соответствие визуальному направлению**. Финальная пиксельная UI/UX-полировка выполняется отдельным этапом; визуальное направление при этом не меняется.

## 16. Платформы

Основной функционал: desktop, mobile browser, Telegram Mini App. На мобильном использовать удобные адаптивные паттерны; основные действия не должны зависеть от горизонтального скролла.

## 17. Роли

Рабочие административные роли: **owner** и **partner**. Не расширять без отдельного требования.

## 18. Правила разработки и экономии Work-лимитов

- Продолжать с текущего состояния проекта; не переписывать приложение с нуля.
- Не проводить повторный полный аудит на каждом этапе, если архитектура существенно не изменилась.
- Этот файл считать постоянным контекстом проекта; в заданиях этапов не требуется повторять содержащиеся здесь требования.
- Перед изменением существующей сущности проверять возможность безопасно расширить её вместо создания новой.
- Не дублировать данные между экранами и модулями.
- Не ломать существующих пользователей и данные; миграции БД выполнять безопасно.
- Не заменять реальные данные mock-данными.
- Не делать глобальный CSS/UI-рефакторинг без необходимости.
- Не менять модули вне scope текущего этапа без технической необходимости.
- После этапа проверять изменённый модуль и связанные критические сценарии. Полный regression test выполнять после крупных блоков, а не после каждой небольшой задачи.
- Сохранять совместимость desktop/mobile/Telegram Mini App и существующую PDF-функциональность.
- Перед крупными изменениями иметь recoverable Git checkpoint/commit.

## 19. Не строить без отдельного этапа

Не требуются без отдельного задания: сложный ERP, складской учёт, бухгалтерская система, сложный Gantt, Trello-клон, глобальная фотогалерея, сложный BI, глобальный редизайн.

## 20. Критерий успеха

Пользователь открывает ADMA, быстро понимает состояние компании, затем открывает объект и в одном месте видит прогресс, деньги, команду, документы, задачи и фото.

Данные связаны без повторного ручного ввода: дизайнер — с заявками/объектами, мастер — с объектами/этапами, финансы — с объектами, фото — с объектами/этапами, общие расходы — отдельно на уровне компании.
