# ADMA Dashboard — Project Specification

Этот файл — постоянный источник требований для разработки ADMA Dashboard. Перед каждым новым этапом следует учитывать его вместе с текущим состоянием проекта. Не нужно повторно проводить полный аудит проекта на каждом этапе, если архитектура существенно не изменилась.

## 1. Цель

Развивать существующий ADMA Finance в единый ADMA Dashboard для управления ремонтными объектами компании. Не переписывать приложение с нуля и не дублировать уже существующие сущности или данные.

Центральная сущность системы — **Объект**.

Целевая логика связей:

- Дизайнер → Заявка → Объект
- Объект → График
- Объект → Финансы
- Объект → Команда
- Объект → Документы
- Объект → Задачи
- Объект → Фото
- Мастер → Объект / Этап
- Общие расходы → ADMA

Одна сущность хранится один раз; разные экраны используют связи и агрегаты, а не копии данных.

## 2. Основная навигация

Целевое главное меню:

- Главная
- Объекты
- Финансы
- Заявки
- Дизайнеры
- Мастера

Отдельный глобальный раздел «График» не нужен. График относится к конкретному объекту. При необходимости общая информация по графикам агрегируется на Главной или может быть добавлена позднее без дублирования модели данных.

## 3. Объекты

Объект — центральная сущность ADMA.

Внутри конкретного объекта целевая навигация:

**Обзор | График | Финансы | Команда | Документы | Задачи | Фото**

Основные данные объекта:

- название / ЖК
- адрес
- площадь
- заказчик
- телефон заказчика
- прораб
- дизайнер
- статус
- процент готовности
- дата начала
- плановая дата сдачи
- фактическая дата сдачи
- номер договора
- гарантийный период
- примечания

Статусы объекта:

- Подготовка
- В работе
- Приостановлен
- Сдача
- Гарантия
- Архив

## 4. Обзор объекта

Обзор должен позволять быстро понять состояние объекта.

Целевые блоки:

- общий прогресс
- текущий и следующий этап
- плановая дата сдачи
- отклонение от графика
- краткая финансовая сводка
- основные ответственные
- блок «Требует внимания»

Не использовать фиктивные production-данные для ещё не реализованных показателей.

## 5. График объекта

Расположение: **Объекты → [Объект] → График**.

Каждый этап связан с конкретным объектом (`object_id`).

Целевые поля этапа:

- название
- плановое начало / окончание
- фактическое начало / окончание
- процент выполнения
- статус
- ответственный
- мастер / команда
- стоимость работ
- комментарий

Статусы:

- Запланирован
- В работе
- Выполнен
- Задерживается
- Приостановлен

Система должна в дальнейшем уметь рассчитывать отклонение от графика. Сложный Gantt не является приоритетом первой версии.

## 6. Финансы объекта

Расположение: **Объекты → [Объект] → Финансы**.

Обязательная структура:

**Сводка | Акты | Накладные | Чеки / Разное**

Не объединять Акты, Накладные и Чеки / Разное в один список.

### Акты

Целевые данные:

- номер
- дата
- название / описание
- этап
- сумма
- связанные оплаты / расходы
- прибыль
- статус
- файл
- комментарий

Формула:

**Сумма акта − связанные оплаты/расходы = прибыль по акту.**

### Накладные

Целевые данные:

- номер
- дата
- поставщик
- описание
- сумма
- связанные оплаты
- остаток
- прибыль
- статус
- файл
- комментарий

Формула:

**Сумма накладной − связанные оплаты = прибыль по накладной.**

### Чеки / Разное

Отдельный раздел для покупок/расходов, суммы которых необходимо получить обратно от заказчика.

**Критическое бизнес-правило: Чеки / Разное НЕ уменьшают прибыль объекта.**

Они учитываются отдельно как суммы к возмещению / получению от заказчика.

Сохранять существующий рабочий PDF-экспорт и связанную с ним логику, если она уже реализована.

## 7. Глобальные Финансы

Главное меню → **Финансы**.

Это не копия финансов конкретных объектов, а агрегированная финансовая картина ADMA.

Целевая структура:

**Сводка | Общие расходы**

### Сводка

В дальнейшем агрегирует:

- прибыль объектов
- суммы к получению
- состояние активных объектов
- общие расходы ADMA
- итоговую прибыль компании

### Общие расходы

Расходы компании, которые не относятся к конкретному объекту и не требуют `object_id`.

Примеры категорий:

- реклама
- сервисы / подписки
- офис
- транспорт
- административные расходы
- зарплаты
- налоги
- банковские расходы
- прочее

Целевые поля:

- дата
- сумма
- категория
- описание
- комментарий
- автор
- файл / чек при необходимости

Целевая формула компании:

**Прибыль всех объектов − Общие расходы = Итоговая прибыль ADMA.**

## 8. Команда и мастера

Внутри объекта раздел **Команда** показывает ответственных и мастеров, назначенных на объект/этапы.

Не создавать копии мастеров внутри объекта. Использовать связь с глобальной базой **Мастера**.

Целевая карточка мастера:

- имя
- телефон
- Telegram
- специализация
- дополнительные навыки
- внутренний рейтинг
- уровень цен
- заметки
- история объектов
- текущая занятость

Занятость:

- Свободен
- Освободится [дата]
- Занят

## 9. Дизайнеры

Глобальный раздел **Дизайнеры** — CRM дизайнеров.

Целевая воронка:

**Найден → Первый контакт → Ответил → Встреча → Партнёр → Передал заявку → Есть объект → Неактивен**

Карточка в дальнейшем содержит контакты, ответственного, последний/следующий контакт, заметки, историю взаимодействий, заявки, объекты и показатели эффективности.

Ключевая связь: **Дизайнер → Заявка → Объект**.

## 10. Заявки

Глобальный раздел **Заявки**.

Целевая воронка:

**Новая → Связались → Замер → Смета → Переговоры → Договор → Проиграна**

Целевые данные:

- клиент
- телефон / Telegram
- объект / ЖК
- площадь
- предполагаемый бюджет
- наличие дизайн-проекта
- желаемый старт
- источник
- ответственный
- комментарии
- история контактов

Источники:

- Дизайнер
- Рекомендация
- Сайт
- Instagram
- Telegram
- Flatica
- Другое

Если источник — дизайнер, использовать связь с конкретным дизайнером CRM.

Успешная заявка должна превращаться в Объект без повторного ручного ввода данных.

## 11. Документы объекта

Категории:

- Договор
- Смета
- Дополнительные соглашения
- Дизайн-проект
- Техническая документация
- Прочее

Акты и Накладные не дублировать здесь как отдельные сущности: они принадлежат Финансам.

## 12. Задачи объекта

Простой операционный менеджер задач, не полноценный Trello.

Целевые поля:

- название
- описание
- ответственный
- дедлайн
- приоритет
- статус

Задача может быть связана с объектом и при необходимости с этапом, актом или накладной.

## 13. Фото объекта

Каждый объект имеет собственный раздел **Фото**.

Фото разных объектов не смешиваются.

Обязательная связь: **Фото → object_id**.

В дальнейшем: **Фото → stage_id** и группировка по этапам. Глобальная фотогалерея в первой версии не нужна.

## 14. Главная

Главная в конечном состоянии — агрегированный dashboard компании.

Целевые группы данных:

- активные объекты и их прогресс
- финансовые показатели
- новые заявки
- активные / просроченные задачи
- задержки
- блок «Требует внимания»

Использовать реальные данные по мере появления модулей; не создавать фиктивные показатели только ради заполнения интерфейса.

## 15. Дизайн

Целевой дизайн ADMA Dashboard задаётся утверждённым GPT Sites макетом пользователя. Ссылка на актуальный визуальный референс должна быть добавлена сюда, когда она окончательно зафиксирована.

Новые экраны должны использовать визуальный язык этого макета:

- композицию
- sidebar / навигацию
- фон
- карточки
- типографическую иерархию
- цветовую палитру
- отступы
- скругления
- кнопки
- таблицы / списки
- фильтры / формы
- бейджи / статусы

Если конкретного экрана нет в макете, использовать существующие паттерны макета вместо создания отдельного стиля.

Приоритет разработки: **архитектура → функциональность → соответствие визуальному направлению**. Финальная пиксельная UI/UX-полировка выполняется отдельным этапом.

## 16. Платформы

Весь основной функционал должен работать:

- desktop
- mobile browser
- Telegram Mini App

На мобильном использовать удобные адаптивные паттерны; основные действия не должны зависеть от горизонтального скролла.

## 17. Роли

Рабочие административные роли системы: **owner** и **partner**. Не расширять ролевую модель без отдельного требования.

## 18. Правила разработки

- Продолжать с текущего состояния проекта.
- Не переписывать приложение с нуля.
- Не проводить повторный полный аудит на каждом этапе, если архитектура существенно не изменилась.
- Перед изменением существующей сущности проверять, можно ли безопасно расширить её вместо создания новой.
- Не дублировать данные между экранами и модулями.
- Не ломать существующих пользователей и данные.
- Миграции БД выполнять безопасно.
- Не заменять реальные данные mock-данными.
- Не делать глобальный CSS/UI-рефакторинг без необходимости.
- Не менять модули вне scope текущего этапа без технической необходимости.
- После этапа проверять изменённый модуль и связанные критические сценарии; полный regression test выполнять после крупных блоков, а не после каждой небольшой задачи.
- Сохранять совместимость desktop/mobile/Telegram Mini App.
- Сохранять существующую PDF-функциональность.
- Перед крупными изменениями иметь recoverable Git checkpoint/commit.

## 19. Не строить без отдельного этапа

Пока не требуются:

- сложный ERP
- складской учёт
- бухгалтерская система
- сложный Gantt
- полноценный Trello-клон
- глобальная фотогалерея
- сложный BI
- глобальный редизайн

## 20. Критерий успеха

Пользователь открывает ADMA и может быстро понять состояние компании, затем открыть конкретный объект и в одном месте увидеть его прогресс, деньги, команду, документы, задачи и фото.

Данные должны быть связаны без повторного ручного ввода: дизайнер связан с заявками/объектами, мастер — с объектами/этапами, финансы — с объектами, фото — с объектами/этапами, а общие расходы учитываются отдельно на уровне компании.
