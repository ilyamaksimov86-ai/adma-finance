# ADMA Dashboard — Project Specification

Этот файл — постоянный источник требований для разработки ADMA Dashboard. Перед каждым новым этапом учитывать его вместе с текущим состоянием проекта. Не повторять полный аудит на каждом этапе, если архитектура существенно не изменилась.

## 1. Цель
Развивать существующий ADMA Finance в единый ADMA Dashboard. Не переписывать backend и рабочую бизнес-логику без необходимости и не дублировать данные.

Центральная сущность — **Объект**.

Связи:
- Дизайнер → Заявка → Объект
- Объект → График / Финансы / Команда / Документы / Задачи / Фото
- Мастер → Объект / Этап
- Общие расходы → ADMA

Одна сущность хранится один раз; экраны используют связи и агрегаты.

## 2. Основная навигация
Главное меню:
- Главная
- Объекты
- Финансы
- Заявки
- Дизайнеры
- Мастера

Отдельный глобальный «График» не нужен. График относится к объекту; общая информация при необходимости агрегируется на Главной.

## 3. Объекты
Внутри объекта: **Обзор | График | Финансы | Команда | Документы | Задачи | Фото**.

Основные данные: название/ЖК, адрес, площадь, заказчик и телефон, прораб, дизайнер, статус, процент готовности, даты начала/плановой и фактической сдачи, номер договора, опциональная сумма договора (информационное поле, не участвует в финансовых расчётах), гарантия, примечания.

Статусы: Подготовка, В работе, Приостановлен, Сдача, Гарантия, Архив.

## 4. Обзор объекта
Быстро показывает общий прогресс, текущий/следующий этап, плановую сдачу, отклонение от графика, краткие финансы, ответственных и «Требует внимания». Не использовать фиктивные production-данные.

## 5. График объекта
**Объекты → [Объект] → График**. Каждый этап связан с `object_id`.

Поля: название, плановое/фактическое начало и окончание, процент выполнения, статус, ответственный, мастер/команда, стоимость работ, комментарий.

Статусы: Запланирован, В работе, Выполнен, Задерживается, Приостановлен. Сложный Gantt не приоритет первой версии.

## 6. Финансы объекта
**Объекты → [Объект] → Финансы**.

Структура: **Сводка | Акты | Накладные | Чеки / Разное**. Не объединять в один список.

### Акты
Номер, дата, название/описание, этап, сумма, связанные оплаты/расходы, прибыль, статус, файл, комментарий.

**Сумма акта − связанные оплаты/расходы = прибыль по акту.**

### Накладные
Номер, дата, поставщик, описание, сумма, связанные оплаты, остаток, прибыль, статус, файл, комментарий.

**Сумма накладной − связанные оплаты = прибыль по накладной.**

### Чеки / Разное
Отдельный раздел для покупок/расходов, суммы которых нужно получить обратно от заказчика.

**Критическое правило: Чеки / Разное НЕ уменьшают прибыль объекта.** Они учитываются отдельно как суммы к возмещению/получению от заказчика.

Сохранять существующий рабочий PDF-экспорт и связанную логику.

## 7. Глобальные Финансы
Главное меню → **Финансы**. Это агрегированная картина ADMA, а не копия финансов объектов.

Структура: **Сводка | Общие расходы**.

Сводка в дальнейшем агрегирует прибыль объектов, суммы к получению, состояние активных объектов, общие расходы и итоговую прибыль ADMA.

### Общие расходы
Расходы компании вне конкретных объектов; `object_id` не требуется. Категории: реклама, сервисы/подписки, офис, транспорт, административные расходы, зарплаты, налоги, банковские расходы, прочее.

Поля: дата, сумма, категория, описание, комментарий, автор, файл/чек при необходимости.

**Прибыль всех объектов − Общие расходы = Итоговая прибыль ADMA.**

## 8. Команда и мастера
Внутри объекта «Команда» показывает ответственных и мастеров, назначенных на объект/этапы. Не создавать копии мастеров — использовать глобальную базу.

Карточка мастера: имя, телефон, Telegram, специализация, дополнительные навыки, рейтинг, уровень цен, заметки, история объектов, занятость.

Занятость: Свободен / Освободится [дата] / Занят.

## 9. Дизайнеры
Глобальный раздел **Дизайнеры** — CRM.

Воронка: **Найден → Нужно изучить → Написал → Ответил → Встреча → Договорились → Передал заявку → Есть объект → Игнор / Отказ**.

Архивирование — отдельный признак записи и не является этапом воронки.

Связь: **Дизайнер → Заявка → Объект**.

## 10. Заявки
Воронка: **Новая → Связались → Замер → Смета → Переговоры → Договор → Проиграна**.

Данные: клиент, телефон/Telegram, объект/ЖК, площадь, бюджет, дизайн-проект, желаемый старт, источник, ответственный, комментарии, история контактов.

Источники: Дизайнер, Рекомендация, Сайт, Instagram, Telegram, Flatica, Другое. Если источник — дизайнер, связывать с CRM. Успешная заявка превращается в Объект без повторного ввода.

## 11. Документы объекта
Категории: Договор, Смета, Дополнительные соглашения, Дизайн-проект, Техническая документация, Прочее. Акты и Накладные не дублировать — они принадлежат Финансам.

## 12. Задачи объекта
Простой операционный менеджер, не Trello-клон. Поля: название, описание, ответственный, дедлайн, приоритет, статус. Возможны связи с объектом, этапом, актом или накладной.

## 13. Фото объекта
Каждый объект имеет собственный раздел **Фото**. Фото разных объектов не смешиваются. Обязательная связь: **Фото → object_id**; в дальнейшем **Фото → stage_id**. Глобальная фотогалерея в первой версии не нужна.

## 14. Главная
В конечном состоянии — агрегированный dashboard: активные объекты и прогресс, финансы, новые заявки, задачи, задержки, «Требует внимания». Использовать реальные данные по мере появления модулей.

## 15. Frontend-основа и дизайн — критически важно

Утверждённый GPT Sites макет ADMA Dashboard:
https://adma-finance-concept.ilyamaksimov86.chatgpt.site/

**Этот GPT Sites-макет является целевой frontend-основой ADMA Dashboard, а не просто визуальным референсом.**

При работе над интерфейсом сначала определить, какие части макета технически возможно переиспользовать напрямую. При возможности максимально переиспользовать его:
- layout и общую композицию;
- sidebar и навигацию;
- структуру Главной;
- UI-компоненты;
- карточки;
- типографику;
- стили и дизайн-токены;
- палитру;
- отступы и размеры;
- скругления и состояния;
- кнопки;
- таблицы/списки;
- фильтры/формы;
- бейджи и статусы.

**Целевой подход:** frontend-макет становится оболочкой приложения, а существующая рабочая бизнес-логика ADMA Finance, реальные данные, маршруты и backend аккуратно интегрируются в эту оболочку.

Не заставлять новый интерфейс наследовать старый дизайн только потому, что существующая логика уже работает. При этом **не переписывать backend, БД и рабочую бизнес-логику ради дизайна**, если их можно безопасно подключить к новой оболочке.

Если исходный код/компоненты GPT Sites доступны и совместимы с текущим стеком — предпочитать переиспользование адаптации вместо ручного воссоздания интерфейса с нуля. Если прямое переиспользование технически невозможно, воспроизвести его паттерны максимально близко в текущем frontend.

Макет определяет дизайн **всего приложения**, не только Главной. Если конкретного экрана в макете нет, строить его из тех же компонентов и паттернов, не придумывая отдельный стиль.

Главная должна максимально сохранять композицию утверждённого макета, заменяя демонстрационные данные реальными данными системы по мере готовности модулей.

Этап 3.5 используется как переход к этой frontend-основе: один раз сформировать правильную оболочку, маршруты и основные экраны, чтобы все последующие этапы разрабатывались уже внутри неё.

Финальная пиксельная UI/UX-полировка выполняется отдельным этапом; направление дизайна после принятия этой основы не меняется.

## 16. Платформы
Основной функционал: desktop, mobile browser, Telegram Mini App. На мобильном использовать удобные адаптивные паттерны; основные действия не должны зависеть от горизонтального скролла.

В будущем планируется отдельный нативный мобильный клиент, в первую очередь iOS, с возможностью дальнейшей поддержки Android. Предпочтительное направление для такого клиента — Expo / React Native, если к моменту реализации не появится более сильная техническая причина выбрать другой подход.

### Архитектура нескольких клиентов — обязательное правило

Все новые backend-функции и бизнес-логика должны проектироваться так, чтобы ими мог пользоваться не только текущий web/Telegram frontend, но и будущий отдельный iOS/Android-клиент.

Не завязывать критическую бизнес-логику исключительно на UI web-приложения или Telegram Mini App.

Backend/API, данные, авторизация, права доступа, файловые операции и бизнес-правила должны оставаться независимыми от конкретного frontend-клиента. Будущий мобильный клиент должен иметь возможность использовать те же данные и функции без переписывания основной системы.

Не создавать отдельный backend для mobile без реальной необходимости. Предпочтительная модель: **один backend и одна БД → web / Telegram Mini App / будущий mobile-клиент**.

API payloads и форматы ошибок должны быть стабильными и по возможности единообразными. При появлении нескольких полноценных клиентов предпочтительно вынести общие API-контракты/схемы в единый source of truth вместо ручного дублирования форматов в каждом клиенте.

Бизнес-правила, расчёты, разрешения и важные state transitions не должны существовать только во frontend-коде, если они должны одинаково работать для нескольких клиентов.

## 17. Роли
Рабочие административные роли: **owner** и **partner**. Не расширять без отдельного требования.

## 18. Правила разработки и экономии Work-лимитов
- Продолжать с текущего состояния; не переписывать приложение с нуля.
- Не проводить повторный полный аудит на каждом этапе, если архитектура существенно не изменилась.
- Этот файл считать постоянным контекстом; в заданиях этапов не повторять содержащиеся здесь требования.
- На этапе 3.5 провести только необходимую проверку совместимости текущего frontend с GPT Sites-основой, а не новый полный аудит backend.
- Перед изменением существующей сущности проверять возможность безопасно расширить её вместо создания новой.
- Не дублировать данные.
- Не ломать существующих пользователей и данные; миграции выполнять безопасно.
- Не заменять реальные данные mock-данными.
- Не менять модули вне scope текущего этапа без технической необходимости.
- После этапа проверять изменённый модуль и связанные критические сценарии. Полный regression test — после крупных блоков, не после каждой мелочи.
- Сохранять desktop/mobile/Telegram Mini App и PDF-функциональность.
- Перед крупными изменениями иметь recoverable Git checkpoint/commit.
- Предпочитать модульный монолит и простые решения на существующей инфраструктуре вместо микросервисов, очередей, брокеров, кешей и другой инфраструктуры без измеримой необходимости.
- Не создавать новую архитектурную абстракцию, если существующий паттерн безопасно решает задачу.
- По мере роста frontend постепенно разделять продуктовую логику по функциональным модулям вместо дальнейшего бесконтрольного роста одного глобального файла; делать это инкрементально, без переписывания приложения ради архитектуры.
- Для каждого этапа использовать минимальный набор тестов на том уровне, где реально может возникнуть регрессия; широкий regression запускать для крупных cross-cutting изменений или release/audit pass.
- Функции, не входящие в текущий этап и не активированные в этом spec, считать отложенными; Work не должен самовольно добавлять их «на будущее».
- При появлении фоновых maintenance-задач сначала использовать возможности текущей БД/Supabase и простые scheduled jobs; не добавлять отдельную queue-инфраструктуру без необходимости.
- После технического разбиения frontend/backend по функциональным границам добавить лёгкий `architecture:check`/contract check, который ловит запрещённые зависимости и расхождение общих API-контрактов. Не внедрять тяжёлую архитектурную платформу ради самой проверки.
- Production frontend использует progressive module loading: первый полезный экран ждёт только critical core data, вторичные модули загружаются в фоне/on demand с дедупликацией запросов и явными loading/error states. После обычного успешного write интерфейс обновляет затронутые сущности из server response без полного `loadCloud`; targeted refresh допустим только для подтверждённых server-side side effects. Списки приватных файлов загружают metadata, а signed URL выдаётся backend по запросу открытия после проверки доступа.
- Live search в CRM и Базе знаний сохраняет смонтированное поле ввода, focus и caret, обновляя только локальный контейнер результатов без API-запросов. Воронки Дизайнеров и Заявок используют общий однострочный горизонтальный scroll-паттерн без page-level overflow на desktop/mobile/Telegram Mini App.

## 19. Не строить без отдельного этапа
Без отдельного задания не требуются: сложный ERP, складской учёт, бухгалтерская система, сложный Gantt, Trello-клон, глобальная фотогалерея, сложный BI.

## 20. Критерий успеха
Пользователь открывает ADMA, быстро понимает состояние компании, затем открывает объект и в одном месте видит прогресс, деньги, команду, документы, задачи и фото.

Интерфейс воспринимается как развитие утверждённого GPT Sites-макета, а не как отдельное приложение, которое лишь похоже на него.

Данные связаны без повторного ввода: дизайнер — с заявками/объектами, мастер — с объектами/этапами, финансы — с объектами, фото — с объектами/этапами, общие расходы — отдельно на уровне компании.

## 21. Capability ledger

Эта секция фиксирует крупные возможности проекта, чтобы следующие Work-сессии не тратили лимиты на повторное выяснение, что уже существует и что пока не требуется.

Статусы:
- **included** — реализовано и является частью рабочей системы;
- **in_progress** — текущий активный этап разработки;
- **deferred** — осознанно отложено до отдельного этапа;
- **removed** — сознательно исключено из текущего продукта; не возвращать без отдельного требования.

| Capability | Status | Note |
| --- | --- | --- |
| Объекты | included | Центральная сущность системы |
| График / этапы объекта | included | Без сложного Gantt |
| Финансы объекта и ADMA | included | Акты, накладные, чеки/разное, общие расходы |
| Команда и Мастера | included | Глобальная база мастеров и назначения |
| Документы объекта | included | Приватное файловое хранение |
| Задачи объекта | included | Простой операционный task manager |
| Фото объекта | included | Приватное хранение, связь с объектом/этапом |
| CRM Дизайнеров | included | Этап 7 завершён; связь с объектами через `projects.designer_id` |
| CRM Заявок | included | Этап 8 завершён; Designer → Lead → Project |
| Финальный агрегированный Dashboard | included | Этап 10 завершён; реальные агрегаты и «Требует внимания» |
| Техническое укрепление | included | Feature-модули, architecture/contract checks и durable Storage cleanup |
| Финальный UI/UX | included | Единая production-дизайн-система внедрена без изменения функциональности |
| База знаний ADMA | included | V1: Техкарты, checklist templates, Косяки, поиск, категории и private attachments |
| Нативное iOS/Android приложение | deferred | Будущий отдельный клиент к существующему backend/API |

| Shared API contracts для web/mobile | included | Проверяемый контракт основных command/file API; изменения additive |
| Глобальная фотогалерея | removed | В первой версии не нужна |
| Сложный Gantt / resource planning | removed | Не требуется без отдельного этапа |
| Складской учёт | removed | Не требуется |
| Полноценная бухгалтерская система | removed | Не требуется |
| Микросервисы / отдельный mobile-backend | removed | Не вводить без измеримой технической необходимости |

При завершении крупного этапа обновлять только соответствующие строки ledger, не переписывая весь spec.

## 22. Roadmap оставшихся этапов

Текущий порядок разработки фиксируется так:

### Этап 8 — Заявки — завершён
CRM заявок реализована, бизнес-цепочка **Дизайнер → Заявка → Объект** замкнута. Успешная заявка превращается в Объект без повторного ручного ввода уже известных данных.

### Этап 9 — удалён
Отдельный глобальный «График» не делать. График остаётся внутри Объекта; нужные агрегаты выводятся на Главной.

### Этап 10 — Главная / Dashboard
Собрать реальный агрегированный экран состояния компании: активные объекты, прогресс, задержки, финансы, суммы к получению, общие расходы, заявки, задачи, просроченные контакты и единый блок «Требует внимания».

### Техническое укрепление
После основных бизнес-модулей выполнить небольшой технический этап без смены стека:
- инкрементально разделить разросшийся frontend по feature-модулям;
- зафиксировать стабильные общие API-контракты там, где это уже даёт пользу web/mobile;
- добавить лёгкий `architecture:check`/contract check;
- добавить автоматическую обработку orphan/`cleanup_pending` файлов через текущую инфраструктуру Supabase/scheduled jobs;
- обновить capability ledger;
- выполнить широкий regression после cross-cutting изменений.

Не переводить проект на Bun/Hono/Prisma, микросервисы или другой backend только ради архитектурного этапа.

### Финальный UI/UX
После технического укрепления пройти все экраны и довести интерфейс до утверждённого GPT Sites-направления: единые размеры, отступы, состояния, карточки, таблицы, формы, mobile/TMA, loading/empty/error states и финальный regression. Это полировка существующего продукта, а не новый редизайн.

### База знаний ADMA
После стабилизации текущей первой версии добавить отдельный глобальный модуль **«База знаний»**, который накапливает производственный опыт ADMA и помогает не повторять ошибки с объектов.

Основные типы материалов:
- **Техкарты** — правильная технология выполнения работ: описание, последовательность, материалы, инструменты, требования/допуски, контроль качества, фото/схемы, вложения, автор и актуальность;
- **Ошибки и решения** — реальный косяк/проблема с объекта → причина → как исправили → как предотвратить повторение → фото/вложения.

Архитектура должна позволять связывать запись базы знаний с реальными сущностями без дублирования данных:
- Объект;
- Этап;
- Фото;
- Мастер/команда, если релевантно;
- категория работ/теги.

Минимальные возможности будущего этапа:
- глобальный поиск;
- категории и теги;
- статусы материала: черновик / утверждено / устарело;
- автор и даты создания/обновления;
- фото, файлы и PDF через существующую приватную storage-архитектуру;
- переход от объекта/этапа к связанным материалам базы знаний;
- возможность видеть повторяющиеся типовые ошибки по мере накопления данных.

В будущем, отдельным расширением после накопления качественных данных, допускается AI-поиск по базе знаний в формате «сталкивались ли мы с такой проблемой?» / «как правильно выполнить этот узел?». Не строить AI/RAG до появления реального корпуса материалов и отдельного задания.

### Mobile — отдельный будущий этап
После стабилизации первой версии Dashboard и Базы знаний можно создавать отдельный Expo / React Native клиент для iOS с возможностью Android. Он должен использовать существующие backend/API/БД/Storage и не создавать параллельную бизнес-логику или второй backend без необходимости.

Work не должен менять этот порядок и начинать следующий этап заранее без отдельной команды.
