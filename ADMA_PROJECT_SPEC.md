# ADMA Dashboard — Project Specification

Этот файл — постоянный источник требований для разработки ADMA Dashboard. Перед каждым новым этапом учитывать его вместе с текущим состоянием проекта. Не повторять полный аудит на каждом этапе, если архитектура существенно не изменилась.

## 1. Цель
Развивать существующий ADMA Finance в единый ADMA Dashboard. Не переписывать backend и рабочую бизнес-логику без необходимости и не дублировать данные.

Центральная сущность — **Объект**.

Связи:
- Дизайнер → Заявка → Объект
- Объект → График / Финансы / Команда / Документы / Задачи / Фото
- Мастер → Объект / Этап
- Общие расходы → ADMA

Одна сущность хранится один раз; экраны используют связи и агрегаты.

## 2. Основная навигация
Главное меню:
- Главная
- Объекты
- Финансы
- Заявки
- Дизайнеры
- Мастера

Отдельный глобальный «График» не нужен. График относится к объекту; общая информация при необходимости агрегируется на Главной.

## 3. Объекты
Внутри объекта: **Обзор | График | Финансы | Команда | Документы | Задачи | Фото**.

Основные данные: название/ЖК, адрес, площадь, заказчик и телефон, прораб, дизайнер, статус, процент готовности, даты начала/плановой и фактической сдачи, номер договора, гарантия, примечания.

Статусы: Подготовка, В работе, Приостановлен, Сдача, Гарантия, Архив.

## 4. Обзор объекта
Быстро показывает общий прогресс, текущий/следующий этап, плановую сдачу, отклонение от графика, краткие финансы, ответственных и «Требует внимания». Не использовать фиктивные production-данные.

## 5. График объекта
**Объекты → [Объект] → График**. Каждый этап связан с `object_id`.

Поля: название, плановое/фактическое начало и окончание, процент выполнения, статус, ответственный, мастер/команда, стоимость работ, комментарий.

Статусы: Запланирован, В работе, Выполнен, Задерживается, Приостановлен. Сложный Gantt не приоритет первой версии.

## 6. Финансы объекта
**Объекты → [Объект] → Финансы**.

Структура: **Сводка | Акты | Накладные | Чеки / Разное**. Не объединять в один список.

### Акты
Номер, дата, название/описание, этап, сумма, связанные оплаты/расходы, прибыль, статус, файл, комментарий.

**Сумма акта − связанные оплаты/расходы = прибыль по акту.**

### Накладные
Номер, дата, поставщик, описание, сумма, связанные оплаты, остаток, прибыль, статус, файл, комментарий.

**Сумма накладной − связанные оплаты = прибыль по накладной.**

### Чеки / Разное
Отдельный раздел для покупок/расходов, суммы которых нужно получить обратно от заказчика.

**Критическое правило: Чеки / Разное НЕ уменьшают прибыль объекта.** Они учитываются отдельно как суммы к возмещению/получению от заказчика.

Сохранять существующий рабочий PDF-экспорт и связанную логику.

## 7. Глобальные Финансы
Главное меню → **Финансы**. Это агрегированная картина ADMA, а не копия финансов объектов.

Структура: **Сводка | Общие расходы**.

Сводка в дальнейшем агрегирует прибыль объектов, суммы к получению, состояние активных объектов, общие расходы и итоговую прибыль ADMA.

### Общие расходы
Расходы компании вне конкретных объектов; `object_id` не требуется. Категории: реклама, сервисы/подписки, офис, транспорт, административные расходы, зарплаты, налоги, банковские расходы, прочее.

Поля: дата, сумма, категория, описание, комментарий, автор, файл/чек при необходимости.

**Прибыль всех объектов − Общие расходы = Итоговая прибыль ADMA.**

## 8. Команда и мастера
Внутри объекта «Команда» показывает ответственных и мастеров, назначенных на объект/этапы. Не создавать копии мастеров — использовать глобальную базу.

Карточка мастера: имя, телефон, Telegram, специализация, дополнительные навыки, рейтинг, уровень цен, заметки, история объектов, занятость.

Занятость: Свободен / Освободится [дата] / Занят.

## 9. Дизайнеры
Глобальный раздел **Дизайнеры** — CRM.

Воронка: **Найден → Первый контакт → Ответил → Встреча → Партнёр → Передал заявку → Есть объект → Неактивен**.

Связь: **Дизайнер → Заявка → Объект**.

## 10. Заявки
Воронка: **Новая → Связались → Замер → Смета → Переговоры → Договор → Проиграна**.

Данные: клиент, телефон/Telegram, объект/ЖК, площадь, бюджет, дизайн-проект, желаемый старт, источник, ответственный, комментарии, история контактов.

Источники: Дизайнер, Рекомендация, Сайт, Instagram, Telegram, Flatica, Другое. Если источник — дизайнер, связывать с CRM. Успешная заявка превращается в Объект без повторного ввода.

## 11. Документы объекта
Категории: Договор, Смета, Дополнительные соглашения, Дизайн-проект, Техническая документация, Прочее. Акты и Накладные не дублировать — они принадлежат Финансам.

## 12. Задачи объекта
Простой операционный менеджер, не Trello-клон. Поля: название, описание, ответственный, дедлайн, приоритет, статус. Возможны связи с объектом, этапом, актом или накладной.

## 13. Фото объекта
Каждый объект имеет собственный раздел **Фото**. Фото разных объектов не смешиваются. Обязательная связь: **Фото → object_id**; в дальнейшем **Фото → stage_id**. Глобальная фотогалерея в первой версии не нужна.

## 14. Главная
В конечном состоянии — агрегированный dashboard: активные объекты и прогресс, финансы, новые заявки, задачи, задержки, «Требует внимания». Использовать реальные данные по мере появления модулей.

## 15. Frontend-основа и дизайн — критически важно

Утверждённый GPT Sites макет ADMA Dashboard:
https://adma-finance-concept.ilyamaksimov86.chatgpt.site/

**Этот GPT Sites-макет является целевой frontend-основой ADMA Dashboard, а не просто визуальным референсом.**

При работе над интерфейсом сначала определить, какие части макета технически возможно переиспользовать напрямую. При возможности максимально переиспользовать его:
- layout и общую композицию;
- sidebar и навигацию;
- структуру Главной;
- UI-компоненты;
- карточки;
- типографику;
- стили и дизайн-токены;
- палитру;
- отступы и размеры;
- скругления и состояния;
- кнопки;
- таблицы/списки;
- фильтры/формы;
- бейджи и статусы.

**Целевой подход:** frontend-макет становится оболочкой приложения, а существующая рабочая бизнес-логика ADMA Finance, реальные данные, маршруты и backend аккуратно интегрируются в эту оболочку.

Не заставлять новый интерфейс наследовать старый дизайн только потому, что существующая логика уже работает. При этом **не переписывать backend, БД и рабочую бизнес-логику ради дизайна**, если их можно безопасно подключить к новой оболочке.

Если исходный код/компоненты GPT Sites доступны и совместимы с текущим стеком — предпочитать переиспользование адаптации вместо ручного воссоздания интерфейса с нуля. Если прямое переиспользование технически невозможно, воспроизвести его паттерны максимально близко в текущем frontend.

Макет определяет дизайн **всего приложения**, не только Главной. Если конкретного экрана в макете нет, строить его из тех же компонентов и паттернов, не придумывая отдельный стиль.

Главная должна максимально сохранять композицию утверждённого макета, заменяя демонстрационные данные реальными данными системы по мере готовности модулей.

Этап 3.5 используется как переход к этой frontend-основе: один раз сформировать правильную оболочку, маршруты и основные экраны, чтобы все последующие этапы разрабатывались уже внутри неё.

Финальная пиксельная UI/UX-полировка выполняется отдельным этапом; направление дизайна после принятия этой основы не меняется.

## 16. Платформы
Основной функционал: desktop, mobile browser, Telegram Mini App. На мобильном использовать удобные адаптивные паттерны; основные действия не должны зависеть от горизонтального скролла.

## 17. Роли
Рабочие административные роли: **owner** и **partner**. Не расширять без отдельного требования.

## 18. Правила разработки и экономии Work-лимитов
- Продолжать с текущего состояния; не переписывать приложение с нуля.
- Не проводить повторный полный аудит на каждом этапе, если архитектура существенно не изменилась.
- Этот файл считать постоянным контекстом; в заданиях этапов не повторять содержащиеся здесь требования.
- На этапе 3.5 провести только необходимую проверку совместимости текущего frontend с GPT Sites-основой, а не новый полный аудит backend.
- Перед изменением существующей сущности проверять возможность безопасно расширить её вместо создания новой.
- Не дублировать данные.
- Не ломать существующих пользователей и данные; миграции выполнять безопасно.
- Не заменять реальные данные mock-данными.
- Не менять модули вне scope текущего этапа без технической необходимости.
- После этапа проверять изменённый модуль и связанные критические сценарии. Полный regression test — после крупных блоков, не после каждой мелочи.
- Сохранять desktop/mobile/Telegram Mini App и PDF-функциональность.
- Перед крупными изменениями иметь recoverable Git checkpoint/commit.

## 19. Не строить без отдельного этапа
Без отдельного задания не требуются: сложный ERP, складской учёт, бухгалтерская система, сложный Gantt, Trello-клон, глобальная фотогалерея, сложный BI.

## 20. Критерий успеха
Пользователь открывает ADMA, быстро понимает состояние компании, затем открывает объект и в одном месте видит прогресс, деньги, команду, документы, задачи и фото.

Интерфейс воспринимается как развитие утверждённого GPT Sites-макета, а не как отдельное приложение, которое лишь похоже на него.

Данные связаны без повторного ввода: дизайнер — с заявками/объектами, мастер — с объектами/этапами, финансы — с объектами, фото — с объектами/этапами, общие расходы — отдельно на уровне компании.
